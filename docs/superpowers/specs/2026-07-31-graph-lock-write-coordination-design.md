## Problem

`graph.lock` (a real kernel `flock` via `fs2`, `crates/infigraph-core/src/lockfile.rs`) exists and is correctly leased per-operation at every existing `write_lock()` call site (`store.rs:197/229/287`, `kuzu_backend.rs:415/523/533/543`) — held only for one write's duration, never for a connection's lifetime. But `GraphStore::open_with_lock_timeout` calls `Database::new()` (`store.rs:123`) **before** it ever touches `WriteLock::acquire_with_timeout` (`store.rs:126`), and that later acquisition only gates schema-init on an already-successfully-opened `Database` — never the open attempt itself. No call site anywhere in `lockfile.rs`, `store.rs`, or `kuzu_backend.rs` gates `Database::new()` from outside.

**Empirically confirmed cross-process (2026-07-31), not just inferred from doc comments.** A throwaway two-OS-process probe (parent holds a writable `kuzu::Database::new()` open; a genuine spawned child process attempts a second writable `Database::new()` on the same path) reproduced the exact collision: `IO exception: Could not set lock on file : <path>`, from Kuzu itself, at open time. Distinct nuance worth recording: the existing same-process test `write_lock_wiring.rs::test_open_initializes_schema_under_write_lock` opens the same path twice **within one process** and does *not* observe this collision at all — `Database::new()` succeeds both times; only `WriteLock` (our own lock) catches the second attempt, via the schema-init gate. This means Kuzu's own lock is process-scoped (most likely POSIX `fcntl`-style, which doesn't self-conflict within a process), not per-open-handle — so the existing test's passing result was never evidence against this design's premise, it simply tests a different (and already-correctly-handled) scenario. The genuine cross-process gap this design closes has no existing regression test at all.

`Database::new(path, config)` (confirmed via `lbug-0.16.0/src/database.rs:123-143`, the pinned dependency's own source) is a combined open-or-create call — like `sqlite3_open`, not a destructive `CREATE DATABASE` — routed through `ffi::new_database` into Kuzu's own C++ engine. `read_only` is just one more flag on that same call. Kuzu enforces its own internal writer-exclusivity *inside* that FFI call, entirely independent of and prior to `graph.lock`. Read-only opens are exempt from this check — confirmed both by `lbug`'s own `test_database_read_only` test and by this session's earlier concurrent reader/writer reproduction test — so a second process's read-only open always succeeds regardless of whether a writer is active. Only writable-vs-writable `Database::new()` collides. This means the design below only needs to solve writer-vs-writer serialization; reads already work correctly (a separate, already-filed bug, `LadybugDB/ladybug#766`, covers occasional read instability under heavy contention — unrelated to this gap).

Two concrete consequences follow from `graph.lock` never gating the open call:

1. **Short-lived writer vs. short-lived writer** (two `infigraph index` runs, CLI vs. `group build`, two concurrent MCP instances) race directly at Kuzu's own `Database::new()` and get an opaque hard failure — none of `graph.lock`'s existing bounded-wait, backoff, or holder-identity diagnostics (`Busy`, `LockInfo`) ever come into play, because the race happens upstream of where `graph.lock` is consulted.
2. **Long-lived writer (the watcher) vs. anyone else.** The watcher (`crates/infigraph-core/src/watch/mod.rs`) keeps a persistent `held_prism: Option<Infigraph>` open across batches on non-Windows — the entire point of upstream PR #43, avoiding the checkpoint-storm bloat that motivated it. Because Kuzu's exclusivity check is keyed on "is a writable handle currently open," not on whether `graph.lock` is held, the watcher's open connection blocks every other writer's `Database::new()` for as long as it stays open — regardless of lock state. This is upstream issue #46's complaint, and it's the same behavior as #43 viewed from the other side: fixing one by construction breaks the other unless something changes.

(Windows already closes and reopens the connection per call — `watch/mod.rs:293-295` — so the watcher-side mechanism below is Unix-specific by construction, matching existing platform behavior; it doesn't need to do anything new on Windows.)

## Design

### Part 1 — Acquire `graph.lock` before `Database::new()`

Every write-mode `Infigraph::open()`/`GraphStore`-opening call site acquires `graph.lock` (existing `lockfile::acquire`, bounded wait + backoff, already used elsewhere in the codebase) **before** calling `Database::new()` with `read_only: false` — not after, as today.

This alone fixes consequence 1 above: short-lived writers are serialized upstream of Kuzu's own exclusivity check and never reach it, so any contention now surfaces as infigraph's own `Busy` error with holder identity, exactly like every other lock in the codebase, instead of Kuzu's opaque failure.

It is **not** sufficient alone for consequence 2: a process that holds `graph.lock` only while actively writing (already true today) but keeps its `Database` object open between writes still blocks every other writer's `Database::new()`, lock or no lock — because the Kuzu-level collision is on the open handle, not on our lock's state. Part 2 is the necessary complement.

### Part 2 — Watcher connection yield on contention

The watcher keeps `held_prism` open across batches for efficiency (PR #43's whole point). To avoid starving other writers (issue #46) without giving up that efficiency win in the common, uncontended case:

1. **Signal path, zero new primitives.** `.infigraph/graph.lock.wanted` is a second lock path, coordinated with the *existing* `lockfile::acquire`/`try_acquire` functions — no new code in `lockfile.rs`. A writer blocked acquiring `graph.lock` also holds `.wanted` (via ordinary `lockfile::acquire`) for the duration of that wait. The watcher's peek is just `lockfile::try_acquire(&wanted_path, "watcher-peek")`: `Ok(Some(guard))` means nobody is waiting — drop the guard immediately and keep the connection open; `Ok(None)` means someone holds it — yield. This is the same `try_acquire` semantics already used everywhere else in the codebase, applied to a second path. Being a real flock (not a touch-file), it inherits `graph.lock`'s own crash-safety property (per `lockfile.rs`'s module doc comment: the OS releases a flock automatically when the holder dies, so no staleness/heartbeat logic is needed) — a contender that crashes mid-wait can't leave a permanent false signal.

2. **Gated by `watch.lock`.** Before creating/checking `.wanted` at all, a contending writer checks `lockfile::read_holder(".infigraph/watch.lock")` (`watch.lock` is a trial-then-long-hold flock, confirmed via `daemon.rs:82-109` — `ensure_daemon_running` probes it and releases immediately, then "the daemon process re-acquires its own long-lived hold on startup," so its `LockInfo` is continuously accurate for the watcher's whole session). If no watcher is running — the common case for most projects most of the time — skip the signal mechanism entirely; the ordinary `graph.lock` bounded wait from Part 1 is sufficient, since whoever else holds it is also short-lived. Only when a watcher is running does `.wanted` get touched at all, since the watcher is the one holder that won't release its `Database` handle on its own before its next batch tick.

3. **Detection reuses the existing `watch.stop` idiom exactly.** The watcher's main loop already checks `sentinel.exists()` for `watch.stop` at the top of every iteration (`watch/mod.rs:162-165`), at the same ~200ms cadence as its `rx.recv_timeout` drain (`watch/mod.rs:303`). The `.wanted` peek is added at the same point in the loop. If it indicates contention: drop `held_prism` (closing the `Database` connection) and `continue` the loop normally — batch accumulation, event draining, and the `watch.stop` check all keep working exactly as before, just without an open connection until the next batch tick reopens one. This was chosen over two alternatives (see below): registering `.wanted` with the existing `notify::Watcher` (same latency, more invasive), and reusing `watch.stop`'s full-stop-and-respawn semantics (meaningfully more expensive and failure-prone — see below).

4. **Reacquire needs no new logic.** The watcher's next batch/periodic tick already goes through `begin_index_op` + `watch_db` (`watch/mod.rs:238-261`, `:185-199`), which — after Part 1's fix — acquires `graph.lock` before reopening `Database`. If still contended, this falls straight into the **already-coded** "busy, retry next window" path (`watch/mod.rs:240-256`), the exact idiom already used today for `begin_index_op` contention. No new retry/backoff code is needed anywhere in the watcher.

### Alternatives considered and rejected

- **Kuzu-native read-only peek** (`open_read_only()` to test for an existing writer, avoiding the need for `.wanted` at all): rejected. Read-only opens succeed regardless of writer presence (confirmed via `lbug`'s own `test_database_read_only` test and this session's concurrency reproduction test), so success/failure carries no information about whether a writer is active. The only way to test writer-presence via Kuzu's own API is a *destructive* writable `Database::new()` probe — it either becomes the writer itself on success, or hits the same opaque hard failure this design exists to avoid.
- **`notify::Event`-based signal** (register `.wanted` with the watcher's existing `RecommendedWatcher` instead of polling): rejected in favor of the sentinel-poll idiom. Same effective latency — both are bounded by the ~200ms loop cadence — but this requires an `ignore_dirs`/`should_ignore` exception for one path under `.infigraph` (which is otherwise fully excluded from the recursive watch, `watch/mod.rs:111`), for no latency benefit over the simpler `.exists()`-style peek that already matches `watch.stop`'s precedent.
- **OS signal (`SIGUSR1`) delivered via `watch.lock`'s PID**: rejected. Real added complexity (signal handler installation, async-signal-safety) for a Unix-only mechanism, when the watcher's persistent-connection behavior is already Unix-specific by construction (Windows already closes/reopens per call) — so this wouldn't even simplify the cross-platform story, just add a second delivery path with no latency win over the already-sub-second file-based signal.
- **Reuse `watch.stop` (full watcher stop) instead of a narrower connection-only yield**: rejected. Three concrete costs a narrower yield avoids: (1) **respawn cost** — `watch.stop` fully exits the loop and process; bringing it back requires `ensure_daemon_running` → `spawn_daemon`, a brand-new process and a full recursive `register_watch_dirs`/`register_subdirs` walk re-registering every subdirectory in the project tree, real overhead on a large repo versus dropping one `Option<Infigraph>`. (2) **Event-loss window** — the existing code comment at `watch/mod.rs:181-184` documents that `notify`'s channel-buffering guarantee ("events aren't lost during a stall... notify's channel just buffers them") depends on the `notify::Watcher` object staying alive and registered; a full stop tears that down entirely, while the narrower yield never touches it. (3) **Ownership/failure-mode risk** — `stop_watch` today is a deliberate, explicitly-owned action; repurposing it for routine per-write coordination means every contending writer also owns "remember to restart the watcher afterward," a new failure mode if that writer crashes or errors first.

## Scope

Covers all writers named in the original request: the watcher (PR #43's persistent connection), explicit CLI writes (`infigraph index`/`index --full`), `group build`/`group index`, and multiple concurrent MCP server instances. Part 1 is a single ordering change applied at every write-mode `Infigraph::open()`/`GraphStore`-opening call site (full enumeration is implementation-plan-level work, not design-level — see Open Questions), plus the `docs.lock` addition covering `DocStore` (see Delivery section above) — a second, independent collision domain with the identical bug pattern but zero prior cross-process protection at all (not even a lease, unlike the code graph's landed-but-incomplete `graph.lock`). Part 2 (the yield mechanism) is specific to the watcher's long-lived connection, since it's the only holder type that keeps a `Database` object open between operations; every other writer already closes its connection as soon as its operation ends, so Part 1 alone is sufficient for them. `DocStore` has no equivalent long-lived-connection holder today, so it needs no Part-2-equivalent yield mechanism — only the ordering fix.

**Explicitly not building:** the full daemon/single-write-coordinator architecture (R2.1.3/R2.3.8's "target architecture" — routing every write through one process per project over IPC, replacing lock-per-call entirely). That remains deliberately deferred to Phase 3 per `DESIGN-hardening.md`'s existing phasing. This design is the lighter mechanism that completes R2.3.7 as scoped for Phase 1/P0.

## Relationship to existing design doc items

- **Completes R2.3.7** ("Per-project write lock — the actual fix for I-4"). The 2026-07-20 write-safety-locks spec's PR 1-2 implemented `graph.lock`'s per-call leasing but did not implement the acquire-before-`Database::new()` ordering (Part 1), nor address the long-lived-connection case (Part 2) — both confirmed missing by this session's source-level investigation of `lockfile.rs`, `store.rs`, and `kuzu_backend.rs`. R2.3.7's text should be updated to reflect `graph.lock` (not `writer.lock`, matching R2.1.1's already-landed implementation naming) and to reference this spec for the concrete mechanism.
- **Directly unblocks upstream PR #43** and resolves its conflict with issue #46: #43's persistent connection stops starving other writers once Part 2 lands, without giving up #43's checkpoint-storm fix in the common uncontended case.
- **Does not touch R2.1.3/R2.3.8** (daemon-based target architecture) — remains Phase 3, unaffected by this work.
