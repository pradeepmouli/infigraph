# DaemonKuzu — A Single-Writer Daemon Architecture for Cross-Process Write Coordination

**Date:** 2026-07-31
**Status:** Approved (design), superseding an earlier same-day design in this file — see History
**Parent:** `docs/DESIGN-hardening.md` — this design pulls **R2.1.3** ("MCP as write coordinator, target architecture") and **R2.3.8** ("Real write coordination... Phase 3, deliberately deferred") forward into now, rather than completing R2.3.7 as originally scoped. `DESIGN-hardening.md` needs a corresponding phasing update (see Relationship section).
**Also resolves:** the direct conflict between upstream PR #43 (persistent watcher DB connection) and upstream issue #46 (watcher starves other writers).

## History — why this supersedes the earlier design in this same file

The original version of this spec (same date) proposed a lighter mechanism: acquire `graph.lock` before `Database::new()`, plus a `.wanted`-signal/yield mechanism so the watcher's persistent connection (PR #43) would close itself under contention. That design was implemented into two full plans (`docs/superpowers/plans/2026-07-31-graph-lock-before-open-ordering.md` and `.../2026-07-31-watcher-connection-yield.md`, both now superseded/obsolete) and submitted for independent review.

The review (model: fable) found four confirmed, blocking problems, the most important being architectural, not a plan-writing slip:

- **The ordering fix doesn't cover the real collision window.** `graph.lock` was only ever proposed to be held briefly (schema-init, or one write call) — not for as long as a `Database` handle stays open. The actual, common failure mode is: process A already has its handle open and is doing normal work, holding no lock at that instant; process B comes along later, acquires the now-free `graph.lock` trivially, and still collides raw with A's still-open handle at `Database::new()`. This session's own earlier empirical cross-process probe (see Problem, below) already exhibited exactly this shape — a parent held its handle open without touching any lock, and a genuine child process's `Database::new()` still failed raw.
- **A prerequisite fix (holding the lock for a handle's whole lifetime) reduces to "only one process can ever have the Database open."** Working through what actually closes that gap — the lock would need to be held from `Database::new()` to `Drop`, not per-operation — led directly to the conclusion that per-process locking of any granularity can't coexist with a long-lived holder (the watcher) without a separate yield mechanism, and that mechanism itself has its own gaps (see below). Once you need one process to be the exclusive, indefinite holder anyway, the natural design is to make that arrangement explicit rather than approximate it with locks.
- **The wipe-on-contention matcher would have silently regressed.** `is_lock_contention_error` (`crates/infigraph-core/src/lib.rs:65-69` on `upstream/main`) recognizes contention only via Kuzu's exact raw error string; converting contention into infigraph's own `Busy` error (different text) would have broken that match, causing a live healthy graph to be wiped instead of the open failing cleanly — reintroducing the exact incident that matcher was built to prevent.
- **The `watch.lock`-gating check assumed fork-only code.** The design's "only signal `.wanted` if a watcher is running" check relied on `watch.lock` carrying an identity payload (via `crate::lockfile`), but the actual `watch.lock` acquisition on the target upstream/PR-43 branches (`crates/infigraph-mcp/src/tools/watch.rs`'s `acquire_project_watch_lock`) uses raw `fs2::FileExt::try_lock_exclusive()` with no payload at all — the gate would never have fired in production.

Working through a fix for the correctness gap converged on the architecture this document now describes — which is, explicitly, "Option B" from this design's very first round of brainstorming (an out-of-process write-coordinator daemon), originally set aside in favor of the lighter mechanism above. That lighter mechanism turned out not to actually work; this is the design that does.

## Problem

`Database::new(path, config)` (confirmed via `lbug-0.16.0/src/database.rs:123-143`, the pinned dependency's own source) is a combined open-or-create call — like `sqlite3_open`, not a destructive `CREATE DATABASE` — routed through `ffi::new_database` into Kuzu's own C++ engine, which enforces its own internal cross-process writer-exclusivity *inside* that call, entirely independent of any lock infigraph itself might hold.

**Empirically confirmed cross-process, not just inferred from doc comments.** A two-OS-process probe (parent holds a writable `kuzu::Database::new()` open, doing no other locking; a genuine spawned child process attempts a second writable `Database::new()` on the same path) reproduced the exact collision: `IO exception: Could not set lock on file : <path>`, from Kuzu itself, at open time. A same-process variant of this same test (`write_lock_wiring.rs::test_open_initializes_schema_under_write_lock`) does **not** observe any collision — `Database::new()` succeeds both times within one process; only infigraph's own `WriteLock` catches the second attempt. Kuzu's lock is process-scoped (most likely POSIX `fcntl`-style, which doesn't self-conflict within a process), so that existing test was never evidence against this problem — it exercises a different, already-correctly-handled scenario.

Read-only opens are exempt from this check entirely — confirmed both by `lbug`'s own `test_database_read_only` test and by this session's earlier concurrent reader/writer reproduction test — so a second process's read-only open always succeeds regardless of whether a writer is active. Only writable-vs-writable `Database::new()` collides; reads never needed coordination and this design doesn't add any (a separate, already-filed bug, `LadybugDB/ladybug#766`, covers occasional read instability under heavy contention — unrelated).

Today, on unmodified upstream, this raw collision isn't a narrow race — it lasts for the entire duration any writer's `Database` handle stays open, which for a real multi-file index run can be seconds to minutes. `is_lock_contention_error` already recognizes Kuzu's raw string and avoids wiping data in this case, so the failure is at least clean today — but it's an immediate hard failure with no bounded wait or retry, so a second writer can never succeed by simply waiting for the first to finish.

**Why the watcher (upstream PR #43) makes this concrete and urgent.** PR #43 keeps a persistent `held_prism: Option<Infigraph>` connection open across batches, specifically to avoid the checkpoint-storm bloat of closing and reopening the database on every small batch. That's the correct fix for its own problem — but it means the watcher's handle can now be open *indefinitely*, with no natural point at which another writer's raw collision would clear on its own. That's upstream issue #46.

## Design

### Architecture

Exactly one process type — the watcher, extended — ever calls `Database::new()` for a **write**. It opens the `Database` once and holds it open persistently (no closing and reopening at all, not even occasionally). It serves two kinds of work through the same event loop: its own file-watch-triggered writes (unchanged from today), and incoming **requests** from other processes, delivered as files dropped into a staging directory it already watches (see Messaging, below).

**Scope: the local Kuzu write path only.**
- **Reads are untouched.** They never had this problem (see Problem, above) and routing them through the daemon would add pure request/poll latency to what's likely the majority of all calls (`search`, `get_stats`, `find_all_references`, etc.) for zero benefit, and would make the daemon a bottleneck for traffic it never needed to touch. Readers keep calling `open_read_only()`/`init_read_only()` directly, exactly as today.
- **Neo4j (`--features remote`, `INFIGRAPH_BACKEND=neo4j`) is untouched.** It's a client-server database, built for concurrent client connections, with its own server-side transaction/locking model — it never had this problem. Remote mode specifically exists to *enable* "parallel multi-repo indexing (impossible in local single-writer mode)" (existing codebase convention, `multi/` subsystem) — routing it through a single Kuzu-holding daemon would defeat the entire reason that mode exists.

**`BackendKind::DaemonKuzu`.** A third backend variant, alongside the existing `BackendKind::Kuzu` (direct local, used by the daemon itself for its own real connection) and `BackendKind::Neo4j` (remote, untouched). `DaemonKuzu` implements the same `GraphBackend` interface as `Kuzu`, but for the write path only — every write call drops a request file and polls for the matching result file instead of executing locally. It's never used for reads. `Infigraph::init()`'s existing backend-selection branch (`lib.rs`, currently `neo4j` vs. default `kuzu`) grows a third case: when Kuzu is selected and this process isn't itself the daemon, select `DaemonKuzu` instead of `Kuzu` for the write path. Callers (CLI commands, MCP tools, `group build`/`index`) never see this decision — they call `.index()`/`.upsert_file()`/etc. exactly as they do today; only the backend selected underneath changes.

*Verified 2026-07-31: every `GraphBackend` write method maps to a file-drop request, not just the lightweight-parameter ones.* Methods taking a plain reference (`remove_file`, `derive_tested_by_edges`, `clear_all_data`, `upsert_repo`, `import_scip_index`, `upsert_similar_edge`) become a request as-is. Methods taking already-computed bulk data (`upsert_file`/`upsert_files_bulk`'s `&[FileExtraction]`, `ingest_structured_data`'s `&[serde_json::Value]`) write that data to a **sibling file** next to the request (same `write_atomic` mechanism, not inlined into the small request/result JSON) and reference its path — genuine OS shared memory was considered and rejected for this: every one of these structs holds heap-allocated `String`/`Vec<T>` fields with process-local pointers, so a raw `mmap`'d segment gives no zero-copy benefit without a position-independent format change (FlatBuffers/Cap'n Proto-style) neither justified nor built here; a sibling file requires the identical serialize/deserialize step either way, with no new dependency. `resolve_calls`/`re_resolve_for_files`'s `Option<&LearnedStore>` needs no file transfer at all — `LearnedStore` is already `Serialize`/`Deserialize` and persisted at a well-known path (`.infigraph/learned/patterns.json`, `LearnedStore::load(root)`), so the daemon loads its own copy directly. `ingest_structured_data`'s payload is already `serde_json::Value` and `SchemaMeta` is small, already-`Deserialize` metadata — neither needs new serialization work, just a sibling file (or, if small enough, inlining directly) rather than special-casing.

**Messaging via file-drop, not a socket.** No new dependency, no `interprocess` crate: the watcher is already a file-event-driven system (`notify`-based), so a request is just another file-change event routed to a different handler. A caller drops a small request file into a staging directory the watcher watches (e.g. `.infigraph/requests/` — needs one small `ignore_dirs`/`should_ignore` carve-out, since `.infigraph` is otherwise fully excluded from the recursive watch, `watch/mod.rs:111`). Requests carry **references, not payloads**: "index these file paths," "import the SCIP file at this path," "reindex this project" — never pre-computed data like a batch of already-parsed `FileExtraction` structs. The daemon does its own parsing/extraction using its own local filesystem access, exactly as it already does today for file-change events; it is not a dumb write-executor for data computed elsewhere. This keeps every request tiny and avoids serializing potentially large batch-import payloads (e.g. a big SCIP index, or thousands of files' extracted symbols) anywhere. For completion, the daemon writes a result file back (matching the request's name plus a suffix) once done; the caller polls for its existence with a timeout — the same bounded-wait-with-backoff idiom already used throughout this codebase (`lockfile::acquire`'s own retry loop), applied to a file instead of a lock.

**Bootstrapping.** Every Kuzu write always routes through the daemon — there's no more "direct, no-daemon-needed" write path for local Kuzu. CLI/MCP/group-build call something like today's `ensure_daemon_running` before dropping any request file, spinning one up on-demand if none is running yet (same on-demand-spawn pattern already used for watch today; matches the sccache-style "auto-spawn on demand" prior art `DESIGN-hardening.md` already cites).

**Atomicity per request.** Each request the daemon serves executes via a fresh `Connection` scoped to that one request — the same convention already established by `write_calls_service_edges` (`detect_dynamic_urls`'s edge writer: one real `Connection` owns its whole `BEGIN`→writes→`COMMIT` sequence, rather than fragmenting a transaction across fresh connections). Applied here at the daemon-serving-a-request level rather than the single-call level it was originally used for.

### What this eliminates

Because nothing but the daemon ever opens the `Database` for write, none of the following — all real, working parts of the earlier (superseded) design — are needed anymore: the `graph.lock`-before-`Database::new()` ordering fix, whole-session-lock-plus-witness-parameter machinery, the `.wanted` signal file, the `watch.lock`-gating check, and the `is_lock_contention_error`/`Busy`-recognition fix. There is no second opener left to coordinate with.

### Alternatives considered and rejected

- **The earlier `graph.lock`-ordering + yield-signal design** (this file's own prior version): rejected — see History, above. Doesn't cover the real collision window (B3), and its `watch.lock`-gating check was built against fork-only code that doesn't exist on the actual target branches (B4).
- **Kuzu-native read-only peek** (`open_read_only()` to test for an existing writer): rejected. Read-only opens succeed regardless of writer presence, so success/failure carries no information about whether a writer is active — confirmed via `lbug`'s own test and this session's reproduction.
- **Real socket-based IPC** (`interprocess` crate — cross-platform Unix socket / named pipe, already flagged as prior art in `DESIGN-hardening.md`'s building-blocks section): considered and rejected in favor of file-drop. The apparent advantage — a socket gives a natural request/response pairing — stops mattering once requests are established as small references rather than bulk payloads (see Messaging, above): a result file the caller polls for (the same bounded-wait-with-backoff idiom already used throughout this codebase) provides the same completion signal with zero new dependency, reusing infrastructure the watcher already has rather than adding a second communication mechanism alongside it.
- **A separate, dedicated coordinator process** (distinct from the watcher, with the watcher itself becoming just one more client): rejected in favor of extending the watcher directly. The watcher is already the one thing that persistently opens the `Database`; making it the coordinator reuses its existing lifecycle (`ensure_daemon_running`, `watch.lock`) instead of standing up and supervising a second process type.
- **Routing Neo4j/remote-mode writes through the same daemon, for architectural uniformity**: rejected. Neo4j never had this problem and remote mode specifically exists to enable concurrent multi-repo writes that local single-writer mode can't — funneling it through a single-Kuzu-holding daemon would defeat its purpose for no benefit.

## Relationship to `DESIGN-hardening.md`

- **Supersedes R2.3.7's original framing** ("acquire before write, hold for the write's duration"). That text described per-process locking; this design makes per-process locking of any granularity unnecessary by having only one process ever hold the write path open. R2.3.7's text should be rewritten to point at this document rather than describing a lock discipline.
- **Pulls R2.1.3 and R2.3.8 forward, out of Phase 3.** Both were explicitly labeled "target architecture... deliberately deferred... bigger lift." This design is that architecture, scoped down to exactly what's needed (write-only, Kuzu-only, requests-not-payloads) rather than the fuller version those items originally sketched. The Phasing section (`DESIGN-hardening.md` §9) needs updating to move this out of Phase 3 and into whichever phase this work is actually scheduled.
- **Directly unblocks upstream PR #43** and resolves its conflict with issue #46: since the watcher is now the sole, intentional long-term holder by design (not an exception being carved out of a general per-process-locking rule), #43's persistent-connection efficiency win and #46's starvation complaint stop being in tension at all.

## Open questions for implementation planning

- Exact request/result file formats and staging directory layout (index request: project root + optional file-path list; SCIP-import request: file path; result: matching today's `IndexResult`/error shape returned by `index_project`, serialized so the polling caller can deserialize it) — implementation-plan-level work.
- Daemon-side request queue/concurrency model: does the daemon serve requests strictly sequentially (simplest, matches "writes are rare and batch-oriented" so throughput isn't a concern), or does it need any internal parallelism? Recommend starting sequential given the stated write frequency, revisiting only if it proves to be a bottleneck.
- Exact `ensure_daemon_running`-equivalent bootstrap sequence for the write path (today's version exists specifically for watch; this needs it to also cover one-shot `infigraph index` with no watcher ever previously started).
- Full enumeration of existing write call sites needing migration to `DaemonKuzu`-aware backend selection (CLI commands, MCP tool write paths, `group build`/`group index`) — implementation-plan-level work.
- Whether `docs.lock`/`DocStore` (a second, independent collision domain discovered during the prior design's planning — `crates/infigraph-docs/src/store.rs`'s `DocStore::open()` has zero cross-process protection today, only a process-local `Mutex`) is folded into this same daemon architecture or fixed separately with a narrower lock-based approach, given it has no long-lived-holder equivalent to the watcher and may not need the full daemon treatment. Not yet decided.
