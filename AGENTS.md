# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, ...) when working with code in this repository.

## Working convention

For any non-trivial analysis, review, or investigation (not routine edits), end with a **confidence** (High/Medium/Low) and a **recommendation** (e.g. merge/hold/needs more info) so the result is decision-ready.

## What this is

Infigraph is an AST-powered code intelligence engine: indexes codebases (62 languages) into a persistent embedded graph database (LadybugDB) with Cypher queries, hybrid search, cross-file call resolution, and MCP tools for AI coding agents. Rust workspace, zero LLM dependency, fully local/offline.

## Build, test, lint

```bash
cargo build --release -p infigraph-cli -p infigraph-mcp
cargo test --all
cargo fmt --all
cargo clippy --all-targets -- -D warnings
```

Requires `cmake`. CI runs fmt-check, clippy, and the full test suite across macOS/Linux/Windows — match locally before pushing.

**Change-safety workflow**: check blast radius before editing a shared/foundational path (e.g. via cross-file reference lookups) — a change in `infigraph-core` can silently break the CLI/MCP crates on top of it. Run targeted tests for the area you touched first, then `cargo test --all` before considering it done — this repo has real process-level integration tests (e.g. under `infigraph-mcp/tests/`), not just unit tests, so `--all` matters. The pre-commit hook (tracked source: `.cargo-husky/hooks/pre-commit`) enforces fmt/clippy across the whole workspace, not just changed files, and then runs four `--ignored` perf tests (`write_lock_perf`, `groups_watch_perf`, `index_perf`; see "CI / toolchain gotchas" for their known flakes; plus `unchanged_content_churn_stays_within_its_measured_bound`, the #183 growth gate, ~28s). Editing that tracked source does **not** update `.git/hooks/pre-commit`: cargo-husky stamps its own version marker on the installed copy and rewrites it only when that marker changes, so an edit silently never takes effect until you `rm .git/hooks/pre-commit` and rebuild — the #183 gate sat committed-but-never-run for exactly this reason — pre-existing unrelated drift elsewhere can block an otherwise-clean change; worth checking `cargo fmt --all -- --check` and `cargo clippy --all-targets -- -D warnings` once at the start of a session to know your baseline.

Release process: `./release.sh <version>` (see README's release section). Windows has a few build quirks around the graph DB's static-lib size and CRT linkage — see root `Cargo.toml` comments.

## Architecture

### Crate layout (`crates/`)

- **`infigraph-core`** — the engine: models, language registry, AST extraction, graph storage, search, cross-file resolution, multi-repo/groups, file watching, SCIP enrichment, and the analysis passes (taint, concerns, reflection, config binding).
- **`infigraph-languages`** — tree-sitter language packs (query files, not Rust code).
- **`infigraph-grammar-plugin`** — runtime ANTLR-based plugin system for languages without a tree-sitter grammar.
- **`infigraph-pipeline-plugin`** — runtime plugin system for data-pipeline metadata extraction.
- **`infigraph-docs`** / **`infigraph-confluence`** — document and wiki indexing, feeding the same search pipeline.
- **`infigraph-cli`** — the `infigraph` binary.
- **`infigraph-mcp`** — the MCP server binary, plus the embedded web UI and session persistence.
- **`lsp-to-scip`** — generic LSP→SCIP bridge for languages without a dedicated SCIP indexer.

### Data flow

Source → AST extraction → cross-file resolution → graph → optional SCIP enrichment → search index. Both local (embedded graph DB) and remote (`--features remote`: Neo4j + Postgres, multi-repo) modes share the same schema — see `docs/REMOTE-MULTI-REPO.md`.

### Cross-cutting invariants worth knowing before editing

- The graph DB is single-writer — write paths take an advisory lock; a new write path needs one too.
- **Reads do not open the stores outside the daemon.** This is the default as of #159 (`backend.selected` = `BackendChoice::Daemon`; auto-starts one if none is listening). An unknown or empty `INFIGRAPH_BACKEND` is a startup error (#74), never a silent fallback -- every `Infigraph::init*` matches `validated_backend()` exhaustively. `DaemonKuzuBackend` (code graph) and `DaemonDocStore` (documents) route every read over a local socket to the daemon's read service. `INFIGRAPH_BACKEND=kuzu` is how a process opts out and opens the graph itself — spell it out rather than *unsetting* the variable, which now means the opposite (`LOCAL_BACKEND`/`BACKEND_ENV` exist for exactly this); `INFIGRAPH_DIRECT_READS=1` is the sole exception, and it is deliberately explicit rather than an automatic fallback — a silent fallback keeps both paths permanently live, which is how `Infigraph::init` and `GraphStore::open_read_only_or_degrade` drifted until one quarantined healthy graphs (5818aa1). A new read belongs on `GraphQuery`/`DocQuery`, which are generic over `QueryExec`, so one query body serves both the local and routed paths; adding it to a backend instead forces a second copy for the routed path.
- **A daemon lives as long as someone leases it (#38, #124).** Clients hold one `Attach` connection per (process, project) via `daemon::lease::hold`, called from `ensure_daemon_for_routed_access` and `ensure_daemon_running_required` (`hold_spawned` for a daemon just spawned, which has not taken `watch.lock` yet) -- a new client entry point must go through one of them or it never keeps a daemon alive. The daemon parks each lease on its own thread (never a read-pool worker) and exits after `daemon_idle.grace_secs` (default 1800, 0 disables) with zero leases, no requests and no work in flight. A daemon never leases itself (`lease::mark_self_daemon`). The client lets go of a lease it has not used for `daemon_idle.client_release_secs` (default 1800, 0 never; unix only): a use is `hold` (every `Infigraph::init`) or an `lease::in_use` guard, which `RemoteExec::query_rows` and `daemon::writes::submit` take -- a new routed transport must take one too, or a long call can have its lease released under it. `lease::pin` and the process's `lease::set_release_guard` veto (MCP: while it runs its own watcher on the root) keep a lease past the period. Control and status travel on the same socket (#155): `daemon::control::{send_control, query_status}` are the only clients, neither leases, and every op declares `DaemonOp::KEEPS_ALIVE` -- a new op that should not extend a daemon's life says `false`, and `ClientFrame::keeps_alive`'s exhaustive match will not compile until it answers. `watch.stop` stays as the out-of-band stop for a daemon that cannot answer; there is no per-role stop file (`watch.stop.docs` was retired). Data writes travel on the same socket too (#204): `daemon::writes::submit` is the only client, a write is acked on admission (so a daemon that dies mid-write reads as `Lost`, not `Incompatible`), and a client that closes its connection has withdrawn it -- the coordinator drops a deferred write whose client is gone, but never cancels one that has started. Bulk payloads ride in `.infigraph/write-tmp/` sidecars. There is no `requests/` directory; a daemon answers any file a pre-#204 client drops there with an error naming its build. The daemon's own writes (compaction, auto-recovery, SCIP import) go through its coordinator port in-process, never the socket.
- **There is exactly one `Database` per graph file in a process.** A second handle cannot see the first's uncommitted WAL and silently serves stale or empty rows (#149). The daemon therefore shares its `Arc<GraphStore>` with the read service and publishes it through `HeldPrism`'s beacon, resolved per request because the prism is opened lazily and dropped on `poison_watch_db`. The documents side is the deliberate exception — it opens `docs.kuzu` per request, and only when the file exists (`DocStore::open_for_read`), because `DocStore::open` holds the process-wide `DB_LOCK` for the store's lifetime and a long-lived one would block the doc watcher's next `DocIndex::init()` forever. That is safe only because the docs writer does not stay open.
- **Document indexing is opt-in per project.** `infigraph_core::docs_switch::docs_enabled(root)` (`[docs] enabled`, default off) is the only question; nothing decides from whether `docs.kuzu` exists. Three writers record it, all through `set_docs_enabled`: the executor `infigraph_docs::ops::index_docs` (on), `ops::clean_docs` (off), and the daemon-start migration (on, only when the key is absent). `DocStore::open` creates a missing store, so only writers may reach it: the executor and the doc watcher's reindex, both under `.infigraph/docs-op.lock` held exclusively, with the watcher re-reading the switch under the lock. Readers go through `DocIndex::open_existing` / `DocStore::open_for_read`, which check for the store before taking the shared lock (a lock file creates its directory, and a read must not bring back a removed `.infigraph/`). A new document reader uses one of those two, never `DocIndex::open` + `init`.
- **Pipeline plugins run only inside a document index run, under the exclusive docs lock** (`infigraph_docs::pipelines::PipelineRun`, called right after `upsert_docs` in `DocIndex::index` and link-following) -- never from a read path, and never from a site that holds only the shared lock (`open_existing`, which is why the Confluence sync does not run them). A plugin is a command, so a project's own `<project>/pipelines` plugins load only when the *user layer* lists the project in `[pipelines] trusted_projects` (`infigraph_core::pipelines_trust`); a project's own config can never trust itself, and a linked worktree is a different root. A plugin failure is a warning in `DocIndexResult::pipeline_warnings`, never an index failure.
- **The stale-document prune runs only on a complete listing and only for local document ids.** `prune_stale_docs` skips when the walk hit any error (a short list reads as "deleted") and never considers ids that are empty or `scheme://` (Confluence pages, manifest nodes), because the disk walk cannot vouch for them.
- **A process group is signalled only by the process that created it, and only before its leader is reaped.** `infigraph_core::child` owns the rules: `lead_own_group` is the one place a spawn asks for a group, `GroupChild` (an MCP worker, stopped TERM, grace, KILL) and `LineChild` signal a group they spawned, and `exited_unreaped` (a `waitid(WNOWAIT)` peek) lets a group be swept while its zombie leader still holds the pgid. A worker started as a member of someone else's group (an old supervisor spawning a newer binary) must never `killpg` it -- that is the MCP client's group -- which is why `kill_own_process_group` refuses unless the caller leads its group. The `infigraph-mcp` worker leads a group of its own so the supervisor can take it down with everything it started (#124).
- **A fallback is added to `infigraph_core::degraded`, or it is invisible (#75).** `DegradedMode` is the one set of degraded modes with one `key`, `message` and `remedy` each; `degraded::gather(root)` is what `doctor`, MCP `get_stats` and the tool footers render (`gather_cached` for the footer, which runs after every tool call and must not wait on a busy daemon). A mode a file can establish is derived in `derived_from_disk`; one only a running process knows is reported with `degraded::live::set`/`clear`, which reaches clients through `StatusReport.degraded` and writes the process's log line itself, so a site adds no `eprintln!` of its own. A daemon overrules a client's own guess for a key only when it lists that key in `StatusReport.judged`: its silence otherwise means "not looked at", not "fine". `gather` never opens a store, starts a daemon, takes a lease or creates `.infigraph/`.
- **A full rebuild keeps only what resolution reads (#150).** After the graph write, `build_full_reindex` calls `FileExtraction::reduce_to_resolution_inputs`, which clears the statements and every symbol field `crate::resolve` does not read; that method is the one list of what resolution reads. A resolver that starts reading another field must stop clearing it there, or the daemon's rebuild silently resolves differently from an incremental index (`tests/resolution_trim.rs` compares the edges). Size a batch of extractions with `estimate_extractions_write_bytes`, which counts as it serializes; never serialize them into a buffer to measure them. An indexer's `.scip` output is checked on arrival by `scip::rejection_on_arrival`, a top-level scan; only the importer and the failed-import cleanup decode it.
- **Machine-wide caps are slot pools (`infigraph_core::slots`, #150).** `SlotPool::scip_indexers()` (`[scip] max_concurrent_indexers`) and `SlotPool::full_reindexes()` (`[index] max_concurrent_reindexes`), both default 2, 0 = no cap, user layer only: a cap is a property of the machine. A slot is an OS file lock under `~/.infigraph/`, so a dead holder frees it at once; there is no queue and no order between waiters. The reindex cap sits at exactly one place, `try_start_full_reindex`, through `daemon::reindex_gate::ReindexGate`, asked before any lock: with no slot free the request stays in `deferred`, nothing is locked and reads are served. It covers a client's `index --full`/`rebuild` and compaction. It does **not** cover a daemon's start (which rebuilds nothing), a whole-project drain, `INFIGRAPH_BACKEND=kuzu` `index --full` (the CLI process rebuilds), or a first routed `index`; and recovery of a faulted graph skips it. A wait is bounded by `reindex_gate::MAX_SLOT_WAIT` (10 minutes), after which the rebuild starts without a slot, and is reported as the degraded mode `reindex-waiting-for-slot`, which is also what the client polls: `WriteOpts::on_slot_wait` takes that time off the client's timeout, for `FullReindex` only. A slot error fails open. New heavy, self-initiated work gets its own named constructor on `SlotPool`, never a second pool type. The MCP `index_project` tool kills its `infigraph index` child after 180s (`INDEX_SUBPROCESS_TIMEOUT`): a rebuild still waiting for a slot then is withdrawn with its client and does not run; one that has started completes.
- Indexing respects `.gitignore`/`.infigraphignore` — don't hand-roll path filtering. The one sanctioned way past them is `[index] include` in `.infigraph/config.toml`, which `ignore_rules` reads itself (via `resolve_project_root`) rather than taking as a parameter, so all six walkers and the watcher honor it with no signature change. It re-admits a subtree by adding it as its own walk root with `parents(false)` — gitignore semantics cannot re-include a path under an excluded directory, so a `!` negation never could have worked. `IgnoreMatcher` carries a second `Gitignore` built only from ignore files below an include root, because a matcher more permissive than the walker has the watcher mark files the indexer never stores (orphaned dirty marks, #189's failure mode). An include overrides `.gitignore` ("not source-controlled") but never the project's own `.infigraphignore` ("not worth indexing"), which keeps applying inside, matched against the path relative to the include root. Absolute entries and `..` are accepted only from `~/.infigraph/config.toml` or the env, never from a project's config, and the two layers union rather than override. An include still has to resolve *inside* the walked project: `scan_changed_files` keys files by `strip_prefix(root)` and silently drops what fails, so out-of-project source belongs in its own project joined by a group, not in an include.
- The graph's edge/node schema is extensible per-language-plugin, not a fixed enum.
- File-watching uses a lock file for cross-process dedup — anything that starts a watcher must hold it for the watcher's lifetime.
- Route/decorator extraction differs by language syntax (query-based vs. AST-sibling-scan) — check both before assuming a language isn't covered.
- SCIP enrichment's scratch files are run-unique (`.infigraph/scip-tmp/<indexer>.<pid>-<nanos>.scip`, `temp_dir()/infigraph_scip_inherits.<pid>.<nanos>.parquet`; #139) because the daemon's own staleness-triggered enrichment can run alongside a user's `scip-enrich`/`index --full`. Producers remove only their own files (the directory only once empty) and sweep `.scip` leftovers older than 6h — put any new scratch file on the same pattern; never `remove_dir_all` a shared scratch dir. `.infigraph/scip-enrich.log` (the detached `scip-enrich` subprocess's stderr) is still one fixed, appended file.
- SCIP import only touches files the graph already has a `File` node for (#114). The indexers are external tools that never read `.gitignore`/`.infigraphignore`, so their output covers ignored paths (`dist/`, a gitignored `scratchpad/` of nested worktrees) and files deleted since they ran; `import_scip_index` partitions documents against `MATCH (f:File)` and skips the rest (`ImportStats::files_skipped`). A Symbol whose `file` names no File node is orphaned by construction — no DEFINES edge, unreachable by the file/prefix removal paths, an `infigraph verify` FAIL — so never write one from any new path either.
- An uncaught C++ exception inside lbug aborts the process with no Rust frame to catch it (#132). Bracket any new lbug write or open with `write_phase::enter(&"...", n)` so the daemon's SIGABRT breadcrumb names it, and run `GraphStore::growth_gate(n).tick()` inside any new long write loop so the runaway-growth breaker (#100) re-checks mid-call, not just at the call boundary. "Loop" is the wrong mental model for where this is needed: a straight-line run of several COPYs needs it just as much. #153 was exactly that — `kuzu_backend`'s `use_csv` fork has two branches, only the per-file one got a gate, and the bulk Parquet branch's four node COPYs carried the graph 21MB → 18486MB inside one call. When auditing, note that edge COPYs are gated only incidentally, by routing through `copy_edges_with_bad_record_retry`.
- Never call `kuzu::Database::new` on an unvalidated path — a truncated/corrupt file can make Kuzu's parser read a bogus size field and request a huge allocation, which aborts the whole process on some platforms (observed on Linux, not macOS) before any `Result` exists to catch it. Check file size against a sane minimum first (see `GraphStore::open`/`DocStore::open`).
- Any "wipe and rebuild on open failure" logic must distinguish transient errors (lock contention, resource pressure) from actual corruption — treating every failure as corruption risks destroying real data mid-race with a concurrent reader/writer.
- `infigraph install` strategies plan; they never write (#170). Each `artifacts::strategy::plan_*` reads its target and returns the complete new content or a skip, and `strategy::settle` is the only thing that writes. That is what makes `install --dry-run` exact: a new strategy or install step (the Claude allowlist is one) returns a `Plan`, because one that writes directly makes the preview silently wrong.

For deeper detail on any of these, see the matching skill/rule (`code-indexing-pipeline` for language/resolution/SCIP/watch; `analysis-subsystems` for multi-repo/taint).

### CI / toolchain gotchas

- CI's `dtolnay/rust-toolchain@stable` floats to whatever "stable" resolves to at run time — a newer clippy than your local toolchain can fail on lints your local run never sees. If local and CI disagree on fmt/clippy, suspect this before assuming a bug — confirm by installing CI's exact version locally (`rustup show active-toolchain` with a temporary `rust-toolchain.toml` override) rather than guessing.
- If a PR gets merged into `main` directly *and* separately into a feature branch, GitHub's synthetic PR-merge-commit computation can silently duplicate content (e.g. two copies of the same test module) even when neither branch alone shows a problem — this only appears in the merge commit itself. Rebase the feature branch onto current `main` to fix it for real, rather than trying to resolve it in a synthetic merge.
- Local test runs under high parallelism (`--test-threads` default) can produce resource-contention failures (e.g. mmap/buffer-manager exhaustion from multiple embedded-DB test processes) that aren't real bugs — always confirm a suspected regression with `--test-threads=1` before treating it as one.
- `infigraph-core --test daemon_protocol_watcher_wiring`'s `watch_loop_serves_write_requests_when_serve_requests_is_true` used to hang reproducibly on one long-lived local dev machine (#58; 5s reply budget, `--test-threads=1`, fresh worktree). Since 4290093 (the watch session builds its language registry once, not twice) and the budget's move to 30s it has not been observed: three isolated runs on 2026-09-02 each passed in ~5s. If it comes back, reproduce at your branch's merge-base in a throwaway worktree before investigating, and note that debug-build registry construction alone can approach several seconds on a loaded machine.
- `cargo test -p infigraph-mcp` (notably `--test groups_watch_perf`) does **not** rebuild the separate `infigraph-cli` binary, yet the test indexes its fixtures by spawning it: `tool_index_project` runs `infigraph index` resolved relative to the test executable (`<target-dir>/debug/infigraph`, falling back silently to whatever `infigraph` is on PATH), and that CLI then auto-starts a daemon from the same binary. After switching between branches with different `lbug` (Kuzu) versions the stale binary used to fail silently ("No results across repos"; the daemon side only logs to `<indexed repo>/.infigraph/daemon.log`, a tempdir for this test). Now the fixture fails up front with a "stale `infigraph` CLI at …" assertion naming both build hashes (#141), every CLI/daemon spawn path warns once per process on a build mismatch (`daemon::warn_if_cli_build_differs`), and `Infigraph::init` refuses a storage-version mismatch instead of wiping (#140). The pre-commit hook builds the CLI before running the test; for a manual run, `cargo build -p infigraph-cli` (same profile as the tests) first.
- `write_lock_perf::test_contended_lock_throughput` (pre-commit hook) gates on the *median* of five warmed-up 4-thread/single-thread ratio samples, bound `8×` by default, and prints every sample (#142). If it fails, rerun the single test (`cargo test -p infigraph-core --test write_lock_perf -- --ignored test_contended_lock_throughput`, seconds) and read the printed samples: a median far beyond the bound is a real regression in the lock path (a clap parse inside the held lock region pushed it to 5/5 failures the day #142 was filed) — investigate, never widen. Only for a machine known to be heavily loaded (load average well above the core count) with a *marginal* median, widen that one run with `INFIGRAPH_TEST_LOCK_CONTENTION_RATIO=<n>`.
- Dedup persists `dedup_state.json` into the nearest ancestor `.infigraph/` of the process cwd (`session_context::dedup_state_path`; `crates/infigraph-mcp/.infigraph/` for that crate's test binaries when the runtime dir exists, otherwise the repo root's) every fifth dedup call. `compression_eval.rs::phase3_dedup_eval` now clears it before and after itself (#136); any new test that drives `apply_seen_dedup` for real must do the same, or it fails on its second run of the day with the "(seen)" placeholder on the first call.
